# Road to 1.0 — Feature Completeness

**Status**: Active — this is the working goal
**Set**: 2026-10-17
**Scope**: every package in this repository

---

## Goal

PIE-QTI targets **feature completeness against the QTI 2.2 and QTI 3.0
specifications and a proper 1.0 release**. Completeness is the driver from here
on: spec-defined behavior is in scope unless this document explicitly lists it
as a host-side boundary, and previously deferred or declined work is re-opened
where it stood between the player and full support.

Before 2026-10-17 several capabilities were de-scoped for lack of an intake
driver — most visibly the PCI spec contract (measured: zero
`portableCustomInteraction` content in ~598,000 intake items, no QTI 3.0
packages). That measurement remains valid data, but it no longer decides scope:
the goal is completeness for its own sake and a 1.0 that can honestly claim full
QTI support, independent of what partner intake happens to carry today.

## 1.0 acceptance criteria

1.0 is cut when all of the following hold:

1. **Spec gaps closed.** Every item in [`docs/SPEC-GAPS-PLAN.md`](../SPEC-GAPS-PLAN.md)
   is Done — G-08 phases 1–3 (spec-conformant PCI runtime), G-13 (structured
   labels + braille data exposure), and G-15 (shared catalog files) all landed
   on 2026-10-17.
2. **PCI portability.** A third-party PCI authored against the QTI 3.0
   specification (registry registration, `getInstance`, `onready`/`ondone`,
   QTI variable JSON, `getState()`) runs unmodified in this player.
3. **Official-suite evidence current.** The private runner's published-candidate
   pin is refreshed and all four QTI 2.2 / 3.0 DELIVERY suites (Basic and
   Advanced) plus the QTI 3.0 Elevated Accessibility profile are green on the
   released candidate.
4. **Transformation completeness.** `pie-to-qti2` emits QTI 2.2 and QTI 3.0;
   remaining lossiness (assessment-level accessibility catalogs, mapping-based
   scoring approximations) is documented at the point of warning, not silent.
5. **Accessibility.** WCAG 2.2 Level AA verification is current for every
   interaction, and the PNP display needs (schemes, polarity, layout, text
   appearance) ship with the player.
6. **Honest status surfaces.** `STATUS.md`, both `QTI-COMPLIANCE.md` files, and
   the READMEs describe the same tree this repository ships — no stale
   "rejected"/"unsupported" claims for shipped work.

The prior production-readiness position stands as the final acceptance step: a
real host integration exercising the players remains the practical test that 1.0
works, and should happen at or before the release. It is no longer the *only*
gate — completeness criteria 1–6 are the plan of record.

## Boundaries that stay (host-side even at 1.0)

These are platform or security boundaries, not completeness gaps. They are
recorded here so "full support" is not read to include them:

- **LTI 1.3 / LTI Advantage, LMS/CMS launch, identity, roster, grade passback,
  persistence, authorization** — host platform concerns.
- **Braille hardware routing, TTS engines, sign-language video players** — the
  player ships the data and the event contracts (`qti-catalog-lookup`); hosts
  provide the capability.
- **Inline `<script>` execution from item content** — never executed; the
  sanitizer strips it. PCI modules are the sanctioned custom-code path, and they
  run behind the host's resolver trust decision.
- **`eval`/`new Function` in response processing** — rejected permanently; the
  AST interpreter implements the full operator set without code evaluation.
- **End-user import product** — hosts build import UX on the transformation
  packages.
- **Official 1EdTech conformance assets in this public repository** — licensing
  boundary; the private clean-room runner stays the certification vehicle.

## Sequencing toward 1.0

1. **PCI phases 1–3** — registry contract, AMD loader and module resolution,
   clean-room conformance evidence: **landed 2026-10-17**
   ([`pci-runtime-and-sandbox-2026-08.md`](pci-runtime-and-sandbox-2026-08.md)).
   G-08 is Done in-repo; browser-level evidence follows the verification
   boundary (it attaches to a published candidate), and third-party content as
   the same-reading check is part of the 1EdTech scoping.
2. **G-15** — manifest-level shared catalogs: **Done** (2026-10-17), like G-13
   (structured labels and braille data exposure; research note in
   `packages/item-player/docs/PNP.md`).
3. **PCI phase 4** — sandboxed per-PCI runner on `qti.pie-framework.org`
   (opt-in hardening; independent of 1–2): **Done** (2026-10-17) — the engine,
   protocol, and deployable runner ship in-repo; the origin deployment follows
   the next release.
4. **Evidence refresh** — publish a candidate, re-pin the official-suite runner,
   run all five certifiable suites; scope PCI content with 1EdTech in parallel.
5. **Stale-docs sweep** — `STATUS.md`, both `QTI-COMPLIANCE.md` files,
   READMEs, `ARCHITECTURE.md` describe the shipping tree.
6. **Cut 1.0.0** — review the accumulated breaking changes (the `PciModule`
   replacement is the largest; pre-1.0 carries no compatibility obligation),
   run the production-host validation, release.
