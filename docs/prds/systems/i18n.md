## Summary

`@pie-qti/i18n` is the framework's translation and locale-formatting system. It provides a thin, type-safe layer over browser-native `Intl` APIs that enables QTI player components to display localized strings without requiring host applications to configure anything. Components accept an optional `i18n?: I18nProvider` prop; when it is absent they fall back to hardcoded English strings via the `??` operator. The host owns the locale: the package reads no storage, and a requested tag negotiates by language to the shipped catalog that serves it (`es-MX` → `es`, `ar_SA` → `ar`, `zh-CN` → `zh-Hans`). Persisting the locale and reloading the page on a switch are opt-in options of `SvelteI18nProvider`.

---

## Background and rationale

### Why a custom package rather than i18next, Fluent, or similar

The framework's bundle budget is strict: the entire player including the default locale must gzip to under 10 KB. Every general-purpose i18n library brings a pluralization engine, a message-format parser, SSR utilities, and plugin infrastructure that together exceed this budget before a single translation key is added. The framework's requirements are narrower: dot-notation key lookup, `{variable}` interpolation, `one`/`other` pluralization, and number/date formatting. All of these are handled by a ~2 KB core plus `Intl.NumberFormat` and `Intl.DateTimeFormat`, which are zero-cost because they ship in every modern browser. A custom package gives full control over the public surface without pulling in unused code.

### Why i18n is an optional prop, not a required context

Assessment items are deployed in many environments: standalone demo pages, LMS iframes, native mobile webviews, internal authoring tools. Many of these environments never display non-English text and have no interest in wiring up an i18n provider. Making i18n optional means components work out of the box in English with no host configuration, and only hosts that actually need localization need to provide a provider. The `??` fallback pattern (e.g. `i18n?.t('common.submit') ?? 'Submit'`) keeps each component self-sufficient; it cannot silently render an empty string or a raw key.

### Why the host owns the locale

A host embedding the players already knows the learner's language — from its session, its user profile or its URL. A library that also reads a stored locale is a second driver: it silently overrides the host's choice with whatever an earlier page wrote, and two hosts on one origin overwrite each other's key. `DefaultI18nProvider` therefore takes its locale from the constructor and nothing else. `SvelteI18nProvider` can write the locale on `setLocale()` and reload the page (`persistLocale`, `reloadOnLocaleChange`), and a host that turns persistence on reads the key back itself at startup.

Components are compiled as Svelte custom elements, and Svelte context and stores do not cross Shadow DOM boundaries, so a host-driven switch on a shared provider object reaches mounted components only through a re-render: the host passes a new provider, sets the `locale` attribute, or opts into the reload.

### Why catalogs are keyed by language

A learner's tag is regional (`es-MX`, `fr-CA`, `ar-EG`) far more often than it is one of the regions a catalog was written for, and the catalogs carry no region-specific wording. Keying them by language (`es`, `fr`, `ar`) and negotiating with RFC 4647 lookup lets every regional variant reach its language. Chinese is keyed by script (`zh-Hans`) because script is what separates its written forms: `zh`, `zh-CN` and `zh-SG` reach it, and `zh-TW`, `zh-HK` and `zh-Hant` render English, since Simplified text is not a Traditional reader's fallback. The tag functions mirror pie-players' `language-tags` module, with a parity test, so a tag negotiates to the same catalog in both repositories.

### Why en is loaded eagerly and other locales lazily

English is the fallback locale for every missing key in every other locale. If the en bundle is not present when a component first renders, the fallback chain breaks and components display raw keys instead of English text. A plain static `import` of en guarantees it is always available and resolvable synchronously in the constructor. Additional locales add ~10 KB gzipped each and sit behind an explicit map of dynamic `import()` calls, one entry per locale; loading them lazily via `loadLocale()` avoids penalizing English-only deployments.

The map is written out rather than generated by `import.meta.glob`. The build is plain `tsc`, which emits `import()` verbatim but leaves the Vite macro in place as a call to a function that exists at build time only — a package published that way throws `TypeError: import.meta.glob is not a function` on module evaluation for every consumer not building through Vite. The trade is a line per locale in `I18n.ts` against a package that evaluates anywhere ESM does; bundlers still see each specifier statically, so per-locale code splitting is unaffected.

### Why partial locale coverage is acceptable

Translation coverage may lag en at any point (all seven locales currently report 100% key coverage, with 8–59 keys per locale still carrying the English value). Missing keys fall through the lookup chain to the en fallback rather than surfacing an error or a raw key. This is preferable to blocking a locale deployment until 100% coverage is reached: a partially-translated UI is better than no translated UI, and the fallback to English is unambiguous and readable. The `bun run check-translations` tool tracks coverage precisely so product teams can prioritize translator work based on actual key counts rather than estimates.

## Functional requirements

- **FR-1:** Components must render a functional English UI when no `i18n` prop is provided.
- **FR-2:** When an `i18n` prop is provided, `t(key)` must return the translation from the first step of the locale's negotiation sequence that has the key, or the en value, or the fallback string — in that priority order — never a raw key or an empty string.
- **FR-3:** `setLocale(locale)` on `SvelteI18nProvider` must load the negotiated catalog and switch the wrapped provider. It must write the locale to `localStorage` (key `pie-qti-locale` unless `storageKey` is given) only with `persistLocale`, and call `window.location.reload()` only with `reloadOnLocaleChange`.
- **FR-4:** No provider may read `localStorage`. The active locale is the constructor argument until `setLocale()` changes it.
- **FR-5:** `loadLocale(locale)` must accept any tag, load the catalog it negotiates to and cache it; concurrent calls share one load, a call for a loaded catalog returns without a module fetch, and a tag no catalog serves resolves without loading.
- **FR-6:** Custom messages passed to `DefaultI18nProvider(locale, customMessages)` must take priority over framework translations for matching keys, while missing keys still fall through to the framework translations.
- **FR-7:** `addCustomMessages(locale, messages)` must deep-merge the provided messages into any previously set custom messages for that locale.
- **FR-8:** `t(key, defaultString)` must return `defaultString` when the key is not found in any locale, rather than returning the key itself.
- **FR-9:** `t(key, { variable: value })` must replace `{variable}` occurrences in the resolved string with the provided value.
- **FR-10:** `plural(key, { count })` must select the CLDR plural category for the active locale with `Intl.PluralRules`, resolve `${key}.${category}`, fall back to `${key}.other` when the catalog does not define that category, then apply interpolation. A locale tag `Intl.PluralRules` rejects degrades to the `one`/`other` split.
- **FR-11:** `formatNumber(value, options?)` and `formatDate(date, options?)` must delegate to `Intl.NumberFormat` and `Intl.DateTimeFormat` respectively, using the current locale.
- **FR-12:** `bun run check-translations` must enumerate all keys from the en locale, report which keys are missing in each non-English locale, and exit non-zero if any keys are missing.
- **FR-13:** `bun run scan-hardcoded` must scan `.svelte` and `.ts` files under a target path and report lines containing string literals that match known translation values, with the suggested `i18n?.t(key) ?? 'fallback'` replacement.
- **FR-14:** `bun run build` must run the translation coverage check before compilation; builds must fail if the check exits non-zero (unless `PIE_QTI_DEV_FAST_BUILD=1` is set).
- **FR-15:** All message keys exported from `@pie-qti/i18n` must be TypeScript-typed as `MessageKey`, derived from the structure of `en.ts`, so that invalid keys produce a compile-time error.
- **FR-16:** `getDirection()` must return `'rtl'` for right-to-left locales and `'ltr'` otherwise, and must not throw for a locale tag `Intl.Locale` rejects.
- **FR-17:** The item body root must carry `lang` and `dir` reflecting the provider's locale and direction, and must carry neither when no provider is supplied — an English-only host keeps whatever direction the page already has.
- **FR-18:** `withLocale(locale)` must return a provider view whose active locale is the argument, must leave the originating provider's active locale unchanged, and must share loaded catalogs with it. A view whose catalog is not yet resident must carry `ready`, a promise that settles when the catalog loads and never rejects; a view over a resident catalog, or a tag no catalog serves, carries none.
- **FR-19:** `<pie-qti-item-player>` must list `locale` in `observedAttributes` and apply it through `withLocale()`, so setting or removing the attribute changes that element's locale in place without a page reload and without affecting other players sharing the provider. When the view carries `ready`, the element renders at once with English filling the gap and renders again once when `ready` settles, unless its provider or locale changed meanwhile.
- **FR-22:** A tag must negotiate along its RFC 4647 lookup sequence with `language-script` inserted before the bare language; a catalog reached by widening must share the request's script. POSIX tags (`ar_SA`, `es_ES.UTF-8`) are accepted and normalized, for lookup and for `Intl` formatting.
- **FR-23:** `Player` and `AssessmentPlayer` must default to an English `DefaultI18nProvider` when the host passes none.
- **FR-20:** The published package must evaluate under any ESM loader — no build-tool macros in shipped code, and no unguarded `process` access.
- **FR-21:** No locale catalog may contain ICU MessageFormat arguments, since the runtime does not parse them and would render the syntax to users.

## Non-functional requirements

- **Accessibility:** The `LocaleSwitcher` reference component must have an accessible `<label>` associated with the `<select>` via `for`/`id`, and the `<select>` must carry an `aria-label` from `i18n.selectLanguageAriaLabel`. All translatable ARIA labels (region labels, live-region announcements, screen-reader-only text) must be in the `accessibility.*` and interaction-specific namespaces; hardcoded ARIA text in components is not acceptable.
- **Performance:** Core i18n logic must gzip to ≤2 KB. en locale must gzip to ≤8 KB. Each additional locale must gzip to ≤8 KB. Total default bundle (core + en) must not exceed 10 KB gzipped. Locale modules must be code-split so that loading a second locale does not block initial render.
- **Cross-platform:** The opt-in `localStorage` write must be guarded with `typeof localStorage !== 'undefined'`. `window.location.reload()` must be guarded with `typeof window !== 'undefined'`. These guards allow the package to be imported in SSR or Node.js test environments without throwing.
- **Security:** No user-supplied content is ever evaluated. Interpolation replaces `{variable}` tokens with string-coerced values; there is no `eval`, `Function()`, or HTML-rendering step in the translation pipeline. Custom messages are treated as trusted data supplied by the host application at initialization time, not as user input.
- **i18n:** The package is itself the i18n layer; no external i18n dependency is permitted. Catalogs are keyed by BCP 47 language or language-script tags; requests may be any BCP 47 or POSIX tag. The `LocaleCode` type is open (`string & {}`) to allow host applications to register locales not shipped with the framework.

## Design decisions

### Opt-in page-reload locale switching

**Decision:** `SvelteI18nProvider.setLocale()` loads the negotiated catalog and switches the wrapped provider. Writing the locale to `localStorage` (`persistLocale`) and reloading the page (`reloadOnLocaleChange`) are opt-in; the provider never reads the key back.

**Rationale:** Svelte custom elements render inside Shadow DOM. Svelte's context API and store subscriptions do not cross the Shadow DOM boundary, so a standard reactive store cannot propagate a locale change from the host page into a mounted web component. The alternatives — a global singleton observable registered on `window`, a `StorageEvent` listener, a custom DOM event bus — each require explicit setup in the host and create coupling between the framework and the host's JavaScript environment. Locale changes during an active assessment session are operationally rare (typically the user selects a locale before starting, not mid-test). A page reload is therefore low-cost in practice for a host that wants one, and eliminates an entire class of synchronization bugs. It is opt-in because a library-side read made the stored value a second locale driver that overrode the host's constructor argument (see *Why the host owns the locale*).

**Alternatives considered:**
- Global reactive store on `window` (`window.__pieQtiI18n`): works across Shadow DOM but creates an implicit global dependency and makes testing harder.
- `StorageEvent` listener: asynchronous; components would need to subscribe and re-render, which reintroduces the Shadow DOM propagation problem.
- CSS custom properties for locale state: only applicable to static string selection, not useful for dynamic key lookup.

**Consequences:** A host that relied on the provider restoring its stored locale and reloading on a switch must now pass both options and read the key at startup itself, as the demo app does. Reloading is not the only path to a new locale: `<pie-qti-item-player locale="ar-SA">` sets the locale declaratively and propagates in place.

The attribute resolves through `I18nProvider.withLocale()` rather than `setLocale()`. Calling `setLocale()` would mutate a provider shared with everything else on the page and, on `SvelteI18nProvider`, reload the document — the two things a per-element override exists to avoid. `withLocale()` returns a view sharing catalogs and loaded-locale bookkeeping by reference, so a second locale is parsed once no matter how many players read it, and two players on one page can render different locales from one provider. The change signal is `attributeChangedCallback` via `observedAttributes`, not a `MutationObserver`: for an element's own attributes the platform already delivers the callback, and an observer would be strictly more machinery for the same event.

A `withLocale()` view whose catalog is still loading carries `ready`. The element renders at once with English filling the gap and renders again once when `ready` settles, guarded per provider and locale so a stale load never re-renders and a provider that sets `ready` on every view cannot loop. `ready` exists only while a catalog is loading for the same reason: a resolved `ready` on every view would schedule a re-render per render.

---

### Optional i18n prop with `??` fallback

**Decision:** Every component declares `i18n?: I18nProvider` as an optional prop. String access uses `i18n?.t('key') ?? 'English fallback'` at the call site.

**Rationale:** Requiring a provider forces every host (including internal tooling, unit tests, and Storybook stories) to configure i18n even when they only ever render English. The optional pattern means the package adds zero friction for English-only deployments. The explicit `??` fallback guarantees that a missing provider never produces an empty string or a thrown error — the fallback is always a readable English string hardcoded at the call site.

**Alternatives considered:**
- Required prop with a default value (`i18n = new DefaultI18nProvider()`): creates a new provider instance per component mount.
- Module-level singleton provider: hidden global state that makes components non-portable and hard to test.
- Svelte context injection: does not cross Shadow DOM boundaries (see above).

**Consequences:** Each component that uses i18n must maintain its own list of English fallback strings. If a translation key is renamed, the fallback strings are not automatically updated. The `bun run scan-hardcoded` tool exists specifically to catch drift between fallback strings and the en locale.

The component layer stays erasable: default-components and section-player import `@pie-qti/i18n` with `import type` only and keep it as an *optional* `peerDependency`, so their built JavaScript does not reference it. Their published `.d.ts` files still reference it in public signatures, so a consumer who skips it types the provider as `any` under `skipLibCheck`.

### English default provider in the players

**Decision:** `Player` (item-player) and `AssessmentPlayer` construct `new DefaultI18nProvider('en-US')` when the host passes no provider, and `@pie-qti/i18n` is a regular `dependency` of both packages.

**Rationale:** The previous stand-in provider returned the key for every `t()` call, so a host that passed none rendered raw keys wherever the player handed that provider to a component: `??` fallbacks never fire on a returned string. An English catalog fixes that at the cost the eager en catalog already budgets for: the package is `sideEffects: false`, en is its only static import, and every other catalog is a dynamic `import()` chunk, so the players pull in the core plus en and nothing else.

**Alternatives considered:**
- Keep the stand-in and fix it to return `undefined`: every caller of the player's provider would need a `??` fallback, which duplicates the en catalog at each call site.

**Consequences:** A host installing either player now installs `@pie-qti/i18n`. The players' bundles carry the core and the en catalog.

---

### Custom package instead of i18next

**Decision:** `@pie-qti/i18n` is a bespoke package with a ~2 KB core.

**Rationale:** The framework needs: key lookup with dot notation, `{var}` interpolation, CLDR-category pluralization, and `Intl`-based number/date formatting. i18next at minimum adds ~9 KB gzipped for the core alone, before plugins for interpolation or `Intl` integration. The bespoke package's core minifies to ~1.2 KB gzipped, and `Intl.PluralRules` supplies the category selection at zero bundle cost. There is no server-side rendering requirement and no ICU MessageFormat requirement.

**Alternatives considered:**
- i18next: too large; plugin ecosystem adds complexity without providing needed features.
- Fluent (Mozilla): runtime is ~12 KB gzipped; FTL syntax is non-trivial to author; no advantage over `Intl` for the pluralization rules needed.
- LinguiJS: requires a compile step and a catalog format that does not fit the framework's TypeScript-native locale files.

**Consequences:** The package does not support ICU MessageFormat syntax (e.g. `{count, plural, one {...} other {...}}`); such a string is not parsed and renders its own source text. Locale catalogs must therefore express plurals as key sub-objects, one entry per CLDR category, which `Intl.PluralRules` then selects between — so multi-form languages are covered, but a message needing two independent counts in one sentence has to be decomposed into parts the call site composes (see `transform.transformed.summary`). Hosts wanting single-string ICU must supply their own `I18nProvider`. A test asserts no catalog contains an ICU argument, because the failure mode is invisible until a user sees the syntax.

---

### Locale coverage strategy

**Decision:** en is the single source of truth for the key schema. Other locales are partially translated and fall back to en for missing keys.

**Rationale:** Requiring 100% coverage before shipping a locale would block localization work indefinitely, since translation is often done incrementally by contractors. The fallback-to-English behavior is unambiguous: users see English text for untranslated strings rather than a key or empty space. The `check-translations` build gate prevents regressions (a key present in one build cannot silently disappear in the next), while the partial-coverage policy allows forward progress.

**Alternatives considered:**
- Block shipping until 100% translated: infeasible given contractor translation timelines.
- Display `[MISSING: key]` for untranslated strings: visible to end users in K-12 assessments; unacceptable UX.
- Crowdin/Phrase integration for automated coverage tracking: adds external dependency; current volume does not justify it.

**Consequences:** Users of partially-translated locales will see English strings for missing keys without any visual indicator that a translation is absent. The `check-translations` report must be reviewed by the i18n maintainer before each release to track coverage trends and prioritize translator work.

---

### TypeScript key inference from en

**Decision:** `MessageKey` is derived from the shape of `en.ts` via a `NestedKeyOfHelper` utility type. The locale file uses `as const` to enable deep literal inference.

**Rationale:** Maintaining a separate type definition for message keys would immediately become stale. Deriving the type from the live locale file means that adding a key to en automatically makes it available (and required) in the TypeScript type, and removing a key causes compile errors at all call sites. This catches translation key renames and deletions at build time rather than at runtime.

**Alternatives considered:**
- Manually maintained string union: would immediately drift from the actual locale file.
- Code generation (`codegen` scripts): adds a build step; the TypeScript inference approach achieves the same result without generated files.

**Consequences:** `MessageKey` only covers keys present in en. Keys in other locales that do not exist in en are invisible to TypeScript. This is by design: en is the canonical schema; extra keys in other locales are treated as translator mistakes and flagged as "obsolete" by `check-translations`.

## Extension points

| Extension point | Interface/type | How to use | Example |
|----------------|---------------|------------|---------|
| Custom i18n provider | `I18nProvider` | Implement all required methods; pass instance as `i18n` prop | Wrap i18next and delegate `t()`, `formatNumber()`, etc. |
| Custom locale messages | `Record<string, LocaleMessages>` constructor parameter | Pass to `DefaultI18nProvider(locale, customMessages)` or call `addCustomMessages()` post-construction | Override `common.submit` with brand-specific copy |
| Additional locale files | Any BCP 47 code + `LocaleMessages` | Register via `addCustomMessages('de', messages)`; custom tags negotiate like catalogs, so `de` serves `de-AT` | Add German translations not shipped by the framework |
| Locale persistence | `SvelteI18nProviderOptions` (`persistLocale`, `storageKey`, `reloadOnLocaleChange`); `DEFAULT_LOCALE_STORAGE_KEY` | Opt in, read the key at app startup and pass it as the initial locale | Remember a learner's language choice across page loads |
| Locale negotiation | `resolveFrameworkLocale`, `languageTagLookupSequence`, `normalizeLanguageTag` | Resolve which shipped catalog serves a tag, or match tags in the host's own catalogs | Show which tags a locale picker will actually translate |
| `LocaleSwitcher` UI | Reference component in `src/components/` | Copy and adapt; not exported from the package's main entry point | Host-branded locale picker |

## Data model / contracts

Key types are defined in `packages/i18n/src/core/I18nProvider.ts` and `packages/i18n/src/core/types.ts`.

### `I18nProvider` interface (invariants not obvious from types)

- `t()` must never return `undefined` or throw. When a key is missing at every level of the fallback chain, it returns either the explicit `defaultString` argument or the raw key string.
- `setLocale()` returns `Promise<void> | void`; callers must `await` it when the return value is a Promise, because `SvelteI18nProvider` uses the async form to load the catalog before switching (and, when opted in, persisting and reloading).
- `ready` is optional and only set on a `withLocale()` view whose catalog is loading. It never rejects; callers render first and re-render once when it settles.
- `plural()`, `formatNumber()`, and `formatDate()` are optional on `I18nProvider`; callers must guard with `?.`.

### `DefaultI18nProvider` lookup chain

For a given key, the provider walks the active locale's negotiation sequence and then the English fallback's (`en-US` → `en`). At each step custom messages keyed to that step come before the framework catalog keyed to it, and a widened step serves only tags of the request's script. For `es-MX` the order is:
1. `customMessages['es-MX']`
2. `customMessages['es']`
3. framework `es`
4. `customMessages['en-US']`, then `customMessages['en']`
5. framework `en`

Custom tags are matched after normalization, so `es_MX` and `es-mx` serve the same step. If every step misses, the explicit `defaultString` argument is returned; if that is also absent, the raw key is returned. No step throws.

### `LocaleCode` type

`FrameworkCatalogCode` is the closed union of the eight catalog keys: `en`, `ar`, `es`, `fr`, `nl`, `ro`, `th`, `zh-Hans`. `FrameworkLocaleCode` adds the earlier regional codes (`en-US`, `ar-SA`, `es-ES`, `fr-FR`, `nl-NL`, `ro-RO`, `th-TH`, `zh-CN`), which remain valid inputs. `LocaleCode` widens this to `FrameworkLocaleCode | (string & {})`, allowing any string while preserving autocomplete. `loadLocale()` accepts any `LocaleCode` and loads the catalog it negotiates to; custom locales are provided via `customMessages`.

### `MessageKey` type

Derived at compile time from the shape of `en.ts` using `NestedKeyOfHelper`. Expressed as dot-notation strings (e.g. `'interactions.choice.correct'`). Adding or removing a key in `en.ts` changes the type without any manual update.

### `localStorage` key

With `persistLocale`, `SvelteI18nProvider` writes `'pie-qti-locale'` (`DEFAULT_LOCALE_STORAGE_KEY`), or `storageKey` when given. Nothing in the package reads it: the host reads it at startup and passes the value as the locale.

### Deep imports

The `./locales/*` export serves the catalogs under their keys (`@pie-qti/i18n/locales/en.js`, `.../zh-Hans.js`). The earlier regional file names are gone.

## Acceptance criteria

### Functional

**AC-1: English fallback without provider**
```
Given: A component that uses i18n is mounted with no i18n prop
When: The component renders
Then: All user-visible strings display their hardcoded English fallback values (e.g., "Submit", "Cancel")
      and no string renders as an empty string or as a raw key like "common.submit"
```

**AC-2: Key lookup with active provider**
```
Given: A DefaultI18nProvider initialized with locale 'es-ES' with es-ES fully loaded
When: i18n.t('common.submit') is called
Then: The return value is "Enviar" (the Spanish translation)
```

**AC-3: Fallback to en for missing key**
```
Given: A DefaultI18nProvider initialized with locale 'nl-NL'
  and the nl-NL locale is loaded
  and the key 'interactions.hotspot.selected' is not present in nl-NL
When: i18n.t('interactions.hotspot.selected') is called
Then: The return value is "Selected:" (the en value)
      and no error is thrown or logged in production mode
```

**AC-4: Variable interpolation**
```
Given: A DefaultI18nProvider with en loaded
When: i18n.t('assessment.question', { current: 3, total: 10 }) is called
Then: The return value is "Question 3 of 10"
```

**AC-5: Explicit default string overrides key fallback**
```
Given: A DefaultI18nProvider with en loaded
When: i18n.t('nonexistent.key', 'My fallback') is called
Then: The return value is "My fallback", not "nonexistent.key"
```

**AC-6: Pluralization — singular**
```
Given: A DefaultI18nProvider with en loaded
When: i18n.plural('plurals.items', { count: 1 }) is called
Then: The return value is "1 item"
```

**AC-7: Pluralization — plural**
```
Given: A DefaultI18nProvider with en loaded
When: i18n.plural('plurals.items', { count: 5 }) is called
Then: The return value is "5 items"
```

**AC-8: Locale persistence and reload are opt-in**
```
Given: A SvelteI18nProvider wrapping a DefaultI18nProvider
  and localStorage is available
When: setLocale('fr-FR') is called without options
Then: localStorage.getItem('pie-qti-locale') is null
  and window.location.reload() is not called
When: setLocale('fr-FR') is called on a provider created with { persistLocale: true, reloadOnLocaleChange: true }
Then: localStorage.getItem('pie-qti-locale') returns 'fr-FR' before the reload fires
  and window.location.reload() is called exactly once
```

**AC-9: A stored locale does not override the host's**
```
Given: localStorage contains 'pie-qti-locale' = 'es-ES'
When: new DefaultI18nProvider('en-US') is constructed
Then: provider.getLocale() returns 'en-US'
```

**AC-10: Custom messages take priority over framework translations**
```
Given: A DefaultI18nProvider('en-US', { 'en-US': { common: { submit: 'Send Answer' } } })
When: i18n.t('common.submit') is called
Then: The return value is "Send Answer", not "Submit"
```

**AC-11: addCustomMessages deep-merges without overwriting sibling keys**
```
Given: A DefaultI18nProvider('en-US') with no custom messages
When: addCustomMessages('en-US', { common: { submit: 'Send' } }) is called
  and i18n.t('common.cancel') is called
Then: The return value is "Cancel" (the framework default is preserved)
  and i18n.t('common.submit') returns "Send" (the custom override is applied)
```

**AC-12: loadLocale caches on second call**
```
Given: A DefaultI18nProvider with fr-FR not yet loaded
When: loadLocale('fr-FR') is called twice in sequence
Then: The second call completes synchronously (no additional module fetch)
  and both calls resolve without error
```

**AC-13: loadLocale for a tag no catalog serves resolves**
```
Given: A DefaultI18nProvider
When: loadLocale('de-DE') is called for a tag no framework catalog serves
Then: The promise resolves without loading a module
  and t() calls under that locale return en values
```

**AC-13a: Regional and POSIX tags negotiate to their language's catalog**
```
Given: A DefaultI18nProvider initialized with locale 'es-MX', 'ar_SA' or 'zh-CN'
When: loadLocale() is called with that locale and i18n.t('common.submit') is called
Then: The return value comes from the es, ar or zh-Hans catalog respectively
```

**AC-13b: Traditional Chinese does not get Simplified**
```
Given: A DefaultI18nProvider initialized with locale 'zh-TW' (or 'zh-HK', 'zh-Hant')
```

## Open questions

- [x] **ICU plural strings in `transform.*` namespace** — resolved: converted to the plural-key convention across all eight locales, no parser added. An ICU parser would have cost more than the entire core to serve six keys, against a package whose reason to exist is the bundle budget. `transform.transformed.summary` interleaved two counts and could not survive as one key; it is now `summary`/`summaryWithAssessments` plus `summaryItems`/`summaryAssessments`, composed by the caller.
- [ ] **ar and zh-Hans catalogs**: Both ship and are listed in the package README's catalog table. Is their translation quality reviewed to the same standard as the other catalogs, or are they still experimental?
- [x] **Shared `localStorage` key across multiple player instances** — resolved: the package no longer reads storage, persistence is opt-in, and `storageKey` names the key per provider. Per-element locales over one provider go through the `locale` attribute and `withLocale()`.
- [ ] **Traditional Chinese catalog**: `zh-TW`, `zh-HK` and `zh-Hant` render English. A `zh-Hant` catalog would serve them; is there demand?
- [x] **RTL support** — resolved: `I18nProvider.getDirection()` returns the writing direction of the active locale, derived from `Intl.Locale.prototype.textInfo` with a primary-subtag fallback for engines that lack it. `ItemBody` reflects it onto the item-body root as `dir`, alongside `lang`. Because `direction` is an inherited CSS property, that single attribute reaches interaction components inside shadow roots with no per-component wiring, and the host page's own chrome is left alone — the player publishes direction for its own subtree only. Both evals in `docs/evals/i18n/rtl-support/evals.yaml` now have an implementation to run against.
