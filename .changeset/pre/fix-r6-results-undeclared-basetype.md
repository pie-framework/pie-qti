The two results-report writers share one undeclared-base-type inference (`inferBaseType`, in the reporting module both `serializeAssessmentResult` and `toAssessmentResultXml` import). A value that no declaration and no serialized field types writes as `boolean` (booleans), `integer` (whole numbers), `float` (fractional numbers) or `string` (anything else); a list types itself by its members — `integer` only when every member is a whole number, `float` when any member is fractional, else its first member's type. **Behavior change:** `toAssessmentResultXml` used to carry its own inference that wrote every undeclared number, and every undeclared list of numbers, as `baseType="float"`, so the same undeclared whole number wrote `integer` from one writer and `float` from the other. Undeclared whole numbers now write `baseType="integer"` — an undeclared whole value is an integer base-type value in QTI's value spaces, and the writers, the PCI variable JSON binding, and the schema-valid output all agree. Declared variables (the overwhelmingly common case) are untouched, and documents remain valid against both results schemas.
