Hot-path work on the response-dispatch path (typing into `textEntryInteraction`/`extendedTextInteraction`, choice clicks, gap drops): the item body no longer rebuilds its whole presentation plan per response change. The plan is now built once per content-bearing input — outcomes (integrated feedback), template and context values, lifecycle, PnP, and the response values the item's content actually prints (`printedVariable` targets declared as responses) — while the mounted interactions keep receiving every new response value without a rebuild. A per-keystroke dispatch no longer deep-clones the response graph several times: the session view freezes the serializer's own fresh copies in place, the transition freeze no longer re-clones the previous and current views, every listener receives the same deeply frozen transition (its unfreezable typed-array leaves stay per-recipient, as pinned), and a response change runs response validation exactly once instead of twice. The body's `qti-change` listener and display-settings application are wired per element identity and per PnP change rather than per dispatch, so the listener interactions dispatch through is no longer momentarily detached on every keystroke. Additive surface: `Player.getResponseIdentifiersPrintedInContent()` and the internal `ItemSessionBinding` gain the same probe.
