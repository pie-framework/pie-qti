The item body's presentation cache no longer hard-skips the built-in `duration` context variable. Round 4 exempted it on the claim that it "renders nowhere", but `duration` is printable: an item whose body or rubric contains `<printedVariable identifier="duration"/>` (legal against any declared variable, and against the QTI built-ins) substituted the elapsed time on every rebuild, while the cache hit on every dispatch after the first — the candidate saw a permanently frozen elapsed time with no diagnostic. The context side of the cache now keys on the same printed-set principle the response side already used: the Player's printed-content scan reports printed *context* identifiers alongside the printed response ones (`Player.getContextIdentifiersPrintedInContent()`, threaded through the internal session binding), and the cache compares exactly the context values the markup prints. An item that prints `duration` re-presents as the elapsed time moves; an item that prints no context variable still never rebuilds on typing. The built-in context classification (`duration`/`numAttempts`/`completionStatus` + declared context variables) is single-sourced with the serializer (`BUILT_IN_CONTEXT_IDENTIFIERS`/`isContextSerialized` in `core/serialization/sessionState`), so the scan and `ItemSessionView.context` cannot drift. No public contract change: the scan method and binding member are internal, as for the response set.
