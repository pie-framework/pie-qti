An interaction whose component the registry cannot resolve (no component renders the type) no longer vanishes from the item body. It previously dropped out of the presentation plan with only a host-side coded `render-failed` report, leaving the candidate a silent gap where a question's interaction should be — while mount/update failures already rendered a visible `role="alert"` placeholder. Registry failures now route through the same placeholder and the same coded error path: `createItemPresentation` records each unresolved interaction in the new `ItemPresentation.failedInteractions` (key, authored slot, interaction data — mounts keep the same keying, so a host reconciling keys sees consistent identities), and the item body stands the shared `qti-interaction-error` alert in the interaction's authored slot, named per interaction type, for as long as the failure stands. The body around it keeps rendering. Additive type surface (`FailedInteractionMount`, the `failedInteractions` member on `ItemPresentation`); the candidate-visible change is the completion of the round-3 render-failed placeholder contract, not a new divergence.
